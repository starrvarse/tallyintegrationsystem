Tally XML API Reference

Everything in this page was confirmed by sending real requests to a live TallyPrime instance and reading the response back — not copied from Tally's own (often incomplete or outdated) documentation. Field names, required-but-undocumented sub-fields, and sign conventions are all here specifically because they were not obvious from Tally's docs.

This page has no dependency on this project's backend. Everything below talks directly to Tally's own XML/HTTP gateway (default http://localhost:9000). Copy any example, point it at your own Tally instance, and it works standalone.

Connecting to Tally

Enable Tally's XML server: F1 (Help) → Settings → Connectivity → Client/Server configuration → set a port (default 9000) and make sure "Enable ODBC" / act as an HTTP server is on. Tally then accepts plain HTTP POST requests with an XML body at http://<host>:<port> — no auth, no headers beyond Content-Type: text/xml.

curl -X POST http://localhost:9000 -H "Content-Type: text/xml" --data-binary @request.xml

Tally accepts plain UTF-8 request bodies fine (no need for UTF-16 despite some older guides claiming otherwise). Response bodies can contain raw control characters (e.g. &#4; as a "not applicable" marker, or literal 0x00–0x1F bytes) that break strict XML parsers — strip [\x00-\x08\x0B\x0C\x0E-\x1F] and the literal string &#4; before parsing.

Request Envelope Basics

Every request is an <ENVELOPE> with a <HEADER> and <BODY>. The <TALLYREQUEST> value decides what kind of operation this is:

TALLYREQUESTUsed for
Export DataReading data — TDL Collection queries, native reports
Import DataWriting data — create / alter / delete masters and vouchers

These two modes have completely different body shapes — see the two pattern sections below.

Collection Request Pattern (Export)

The most useful read mechanism is a native Collection request. It reads straight off Tally's internal object model — no TDL report needs to exist on the Tally side. List the exact fields you want with <FETCH> tags.

<ENVELOPE>
 <HEADER>
  <VERSION>1</VERSION>
  <TALLYREQUEST>Export Data</TALLYREQUEST>
  <TYPE>Collection</TYPE>
  <ID>MyCollection</ID>
 </HEADER>
 <BODY>
  <DESC>
   <STATICVARIABLES>
    <SVEXPORTFORMAT>$$SysName:XML</SVEXPORTFORMAT>
    <!-- optional, needed for Vouchers: -->
    <SVFROMDATE>20250401</SVFROMDATE>
    <SVTODATE>20260331</SVTODATE>
   </STATICVARIABLES>
   <TDL>
    <TDLMESSAGE>
     <COLLECTION NAME="MyCollection" ISMODIFY="No">
      <TYPE>Ledger</TYPE>
      <FETCH>NAME</FETCH>
      <FETCH>PARENT</FETCH>
      <FETCH>OPENINGBALANCE</FETCH>
     </COLLECTION>
    </TDLMESSAGE>
   </TDL>
  </DESC>
 </BODY>
</ENVELOPE>

Swap <TYPE>Ledger</TYPE> for any native object type (Company, Group, StockItem, StockGroup, StockCategory, Unit, TAXUNIT, Voucher…). Requesting a nested list field (e.g. ADDRESS.LIST) auto-expands its children — you don't need to enumerate the sub-fields.

You can fetch every field a type has with <FETCH>*</FETCH> Extremely useful for discovering field names Tally's docs don't mention. Only use it for masters — never combine a date-range (SVFROMDATE/SVTODATE) with StockItem + wildcard fetch; on this Tally build it hung the entire XML server for about a minute across all 1000+ items.

Company

The company's own address is not under ADDRESS.LIST (that only works for Ledgers). It's flattened into a single comma-joined string:

<FETCH>NAME</FETCH>
<FETCH>REMOTEFULLLISTNAME</FETCH>  <!-- flattened multi-line address -->
<FETCH>STATENAME</FETCH>
<FETCH>COUNTRYNAME</FETCH>
<FETCH>PINCODE</FETCH>
<FETCH>EMAIL</FETCH>
<FETCH>WEBSITE</FETCH>
<FETCH>PHONENUMBER</FETCH>
<FETCH>MOBILENO</FETCH>          <!-- not "MOBILENUMBER" -->
<FETCH>INCOMETAXNUMBER</FETCH>   <!-- PAN -->
<FETCH>CORPORATEIDENTITYNO</FETCH> <!-- CIN -->
<FETCH>STARTINGFROM</FETCH>
<FETCH>BOOKSFROM</FETCH>

Splitting REMOTEFULLLISTNAME on commas gives you back the address lines. Example real value: "MANKACHAR JAME MASJID, 0, GROUND FLOOR, MASJID COMPLEX, MAIN ROAD, MANKACHAR, SOUTH SALMARA MANKACHAR, FSSAI: 10320007000020".

The Company object does NOT carry the company's own GSTIN. GSTREGISTRATIONNUMBER exists as a field but is reliably empty in TallyPrime 5+. See GST Registration (TAXUNIT) below — this is a separate object entirely.

GST Registration TYPE=TAXUNIT

In TallyPrime 5+, a company's GST registration(s) are their own master object — internally typed TAXUNIT — supporting multiple registrations (branches/states) per company. A single-registration company still gets exactly one real TAXUNIT record, plus an unrelated "Default Tax Unit" placeholder with no GSTIN (filter it out by requiring a non-empty GSTIN).

<TYPE>TAXUNIT</TYPE>
<FETCH>NAME</FETCH>
<FETCH>GSTREGNUMBER</FETCH>
<FETCH>PAN</FETCH>
<FETCH>GSTEINVBILLFROMPLACE</FETCH>
<FETCH>GSTREGISTRATIONDETAILS.LIST</FETCH>
<!-- nested: STATE, REGISTRATIONTYPE, PLACEOFSUPPLY, GSTR1PERIODICITY -->

Ledger

<TYPE>Ledger</TYPE>
<FETCH>NAME</FETCH>
<FETCH>PARENT</FETCH>
<FETCH>ADDRESS.LIST</FETCH>
<FETCH>STATE</FETCH>                <!-- often empty; see PRIORSTATENAME -->
<FETCH>PRIORSTATENAME</FETCH>       <!-- reliable fallback for state -->
<FETCH>COUNTRYNAME</FETCH>
<FETCH>PINCODE</FETCH>
<FETCH>LEDGERMOBILE</FETCH>
<FETCH>EMAIL</FETCH>
<FETCH>INCOMETAXNUMBER</FETCH>      <!-- PAN -->
<FETCH>ISBILLWISEON</FETCH>
<FETCH>OPENINGBALANCE</FETCH>
<FETCH>CLOSINGBALANCE</FETCH>
<FETCH>LEDGSTREGDETAILS.LIST</FETCH> <!-- real GSTIN lives here, see below -->
<FETCH>LANGUAGENAME.LIST</FETCH>    <!-- alias is the 2nd <NAME> here -->
A party's GSTIN is NOT under PARTYGSTIN. That flat field is legacy and empty on every real ledger we checked (0 of 295). The live value is nested: 
LEDGSTREGDETAILS.LIST
  GSTREGISTRATIONTYPE  → "Regular"
  STATE
  GSTIN                → the real GSTIN
  PLACEOFSUPPLY
Alias is not a flat <ALIAS> field. It's the second <NAME> entry inside LANGUAGENAME.LIST/NAME.LIST (the first is the primary name). This is true for every master type except Unit, which doesn't support alias at all — see Gotchas.

Group Ledger Groups

<TYPE>Group</TYPE>
<FETCH>NAME</FETCH>
<FETCH>PARENT</FETCH>             <!-- "Primary" for top-level groups -->
<FETCH>ISDEEMEDPOSITIVE</FETCH>   <!-- Yes = Debit-natured, No = Credit-natured -->
<FETCH>AFFECTSGROSSPROFIT</FETCH>
<FETCH>ISSUBLEDGER</FETCH>

Stock Item

<TYPE>StockItem</TYPE>
<FETCH>NAME</FETCH>
<FETCH>PARENT</FETCH>
<FETCH>BASEUNITS</FETCH>
<FETCH>ADDITIONALUNITS</FETCH>
<FETCH>DENOMINATOR</FETCH>         <!-- alt-unit ratio, see Gotchas -->
<FETCH>OPENINGBALANCE</FETCH>      <!-- e.g. " 180 PCS =  15 CASE" -->
<FETCH>OPENINGVALUE</FETCH>        <!-- sign is inverted, see Sign Conventions -->
<FETCH>OPENINGRATE</FETCH>         <!-- e.g. "201.40/PCS" -->
<FETCH>CLOSINGBALANCE</FETCH>
<FETCH>CLOSINGVALUE</FETCH>
<FETCH>GSTTYPEOFSUPPLY</FETCH>     <!-- "Goods" / "Services" -->
<FETCH>HSNDETAILS.LIST</FETCH>     <!-- nested: HSNCODE -->
<FETCH>GSTDETAILS.LIST</FETCH>     <!-- nested, see below -->

GSTDETAILS.LIST nests three levels deep:

GSTDETAILS.LIST
  TAXABILITY                    → "Taxable" / "Exempt" / "Nil Rated"
  STATEWISEDETAILS.LIST
    STATENAME                   → literal "&#4; Any" for all-states
    RATEDETAILS.LIST (repeated, one per duty head)
      GSTRATEDUTYHEAD            → "CGST" / "SGST/UTGST" / "IGST" / "Cess" / "State Cess"
      GSTRATEVALUATIONTYPE       → "Based on Value"
      GSTRATE                    → the percentage

Stock Group / Stock Category

<TYPE>StockGroup</TYPE>    <!-- or StockCategory -->
<FETCH>NAME</FETCH>
<FETCH>PARENT</FETCH>

Unit

<TYPE>Unit</TYPE>
<FETCH>NAME</FETCH>
<FETCH>ISSIMPLEUNIT</FETCH>
<FETCH>BASEUNITS</FETCH>            <!-- only for compound units, e.g. KG.GM -->
<FETCH>CONVERSION</FETCH>
<FETCH>DECIMALPLACES</FETCH>
<FETCH>REPORTINGUQCDETAILS.LIST</FETCH> <!-- nested: REPORTINGUQCNAME, the GST UQC code -->
The Unit master's own BASEUNITS/CONVERSION is NOT what a stock item's alternate-unit ratio uses. These describe genuine compound units (e.g. a unit literally named "KG.GM"). Every simple unit has CONVERSION=0. A stock item's own "1 CASE = 12 PCS" ratio lives on the stock item, not the unit — see below.

Voucher

Requires SVFROMDATE/SVTODATE in STATICVARIABLES (see the pattern example above).

<TYPE>Voucher</TYPE>
<FETCH>DATE</FETCH>
<FETCH>VOUCHERTYPENAME</FETCH>
<FETCH>VOUCHERNUMBER</FETCH>
<FETCH>PARTYLEDGERNAME</FETCH>
<FETCH>NARRATION</FETCH>
<FETCH>GUID</FETCH>
<FETCH>ALLLEDGERENTRIES.LIST</FETCH>    <!-- nested: LEDGERNAME, AMOUNT -->
<FETCH>ALLINVENTORYENTRIES.LIST</FETCH> <!-- nested: STOCKITEMNAME, BILLEDQTY, RATE, AMOUNT -->

The voucher's own VCHTYPE attribute (on the <VOUCHER> tag itself) is a more reliable voucher-type label than the VOUCHERTYPENAME field in some edge cases.

To get one specific party's ledger statement: fetch all vouchers for the date range, then filter client-side for any voucher whose ALLLEDGERENTRIES.LIST contains an entry with that party's LEDGERNAME. Tally has no server-side "vouchers for this ledger" collection filter that's worth the complexity.
This bare TYPE=Voucher Collection silently excludes Journal, Credit Note, and Debit Note — confirmed live: genuinely-committed vouchers of those types, visible in Tally's own Day Book, simply never appear in the result, with no error or indication anything was filtered. Sales/Purchase/Receipt/Payment/Contra come through fine. If you need those three types, use the Voucher Register report instead (REPORTNAME=Voucher Register, Export Data, with a VOUCHERTYPENAME static variable) — heavier (dumps every field, not just your FETCH list) but complete.
SVFROMDATE/SVTODATE is silently ignored on this same bare Collection — a single-day range still returned the company's entire voucher history in testing. Filter by the returned DATE field client-side instead of trusting the server to have scoped it. (The Voucher Register report, unlike the Collection, does respect the date range correctly.)
Reads can lag a write by minutes, through every read path — Collection and Voucher Register alike. A freshly created/altered/deleted voucher is genuinely committed (visible immediately in Tally's own GUI/Day Book) but an XML read a few seconds later can still show the pre-write state. This wasn't a bug in the read queries; it self-resolved after enough real time passed, and a full Tally restart did not visibly force a refresh. If you're building a UI on this API, don't depend on a re-fetch to reflect a write you just made — update your local state optimistically from what you sent instead.

Import Request Pattern (Write)

Writes use a totally different envelope shape from reads: IMPORTDATA / REQUESTDATA / TALLYMESSAGE, with each master or voucher as a direct child carrying an ACTION attribute.

<ENVELOPE>
 <HEADER>
  <TALLYREQUEST>Import Data</TALLYREQUEST>
 </HEADER>
 <BODY>
  <IMPORTDATA>
   <REQUESTDESC>
    <REPORTNAME>All Masters</REPORTNAME>
   </REQUESTDESC>
   <REQUESTDATA>
    <TALLYMESSAGE xmlns:UDF="TallyUDF">
     <LEDGER NAME="Some Ledger" ACTION="Create">
      <!-- fields -->
     </LEDGER>
     <!-- you can batch multiple TALLYMESSAGE children of different types
          in one request; each gets its own ACTION -->
    </TALLYMESSAGE>
   </REQUESTDATA>
  </IMPORTDATA>
 </BODY>
</ENVELOPE>

ACTION is one of Create, Alter, Delete, Cancel. The response is a flat counter block, not an echo of your data:

<RESPONSE>
 <CREATED>1</CREATED>
 <ALTERED>0</ALTERED>
 <DELETED>0</DELETED>
 <ERRORS>0</ERRORS>
 <EXCEPTIONS>0</EXCEPTIONS>
 <!-- a <LINEERROR> tag appears here on failure, with a human-readable message -->
</RESPONSE>
A "successful" response does not mean every field was saved. This is the single biggest trap in Tally's Import API: an invalid or misplaced field inside a nested list is silently dropped — Tally still reports CREATED>1 with zero errors, but the field (and sometimes everything after it in that nested list) is just missing. Always read the record back after writing it to confirm. Every field on this page was verified this way.

Create / Alter a Ledger

<LEDGER NAME="ABC Traders" ACTION="Create">
 <LANGUAGENAME.LIST>
  <NAME.LIST>
   <NAME>ABC Traders</NAME>
   <NAME>ABC</NAME>               <!-- alias: 2nd <NAME>, optional -->
  </NAME.LIST>
 </LANGUAGENAME.LIST>
 <PARENT>Sundry Debtors</PARENT>
 <OPENINGBALANCE>-32100</OPENINGBALANCE>  <!-- negative = Debit, see Sign Conventions -->
 <ISBILLWISEON>Yes</ISBILLWISEON>
 <EMAIL>accounts@abctraders.com</EMAIL>
 <LEDGERMOBILE>9999999999</LEDGERMOBILE>
 <INCOMETAXNUMBER>ABCDE1234F</INCOMETAXNUMBER>  <!-- PAN -->

 <LEDMAILINGDETAILS.LIST>
  <APPLICABLEFROM>20250401</APPLICABLEFROM>  <!-- MUST equal company's books-from date -->
  <MAILINGNAME>ABC Traders</MAILINGNAME>
  <ADDRESS.LIST>
   <ADDRESS>123 Market Street</ADDRESS>
   <ADDRESS>Guwahati</ADDRESS>
  </ADDRESS.LIST>
  <STATE>Assam</STATE>
  <COUNTRY>India</COUNTRY>
  <PINCODE>781001</PINCODE>
 </LEDMAILINGDETAILS.LIST>

 <LEDGSTREGDETAILS.LIST>
  <APPLICABLEFROM>20250401</APPLICABLEFROM>  <!-- MUST equal company's books-from date -->
  <GSTREGISTRATIONTYPE>Regular</GSTREGISTRATIONTYPE>
  <GSTIN>18ABCDE1234F1Z5</GSTIN>
  <PLACEOFSUPPLY>Assam</PLACEOFSUPPLY>
 </LEDGSTREGDETAILS.LIST>
</LEDGER>
APPLICABLEFROM must be the company's actual books-from date, not "today". Using an arbitrary date (e.g. the current date) causes Tally to silently drop the rest of that master's fields — no error. Read it once via Company/BOOKSFROM or Company/STARTINGFROM and reuse it for every write.
To Alter, resend the exact same shape with ACTION="Alter". Confirmed live: re-sending LEDGSTREGDETAILS.LIST/LEDMAILINGDETAILS.LIST with the same APPLICABLEFROM date cleanly replaces the existing entry — it does not append a duplicate dated history entry.

Create / Alter a Stock Item

<STOCKITEM NAME="Widget A" ACTION="Create">
 <LANGUAGENAME.LIST>
  <NAME.LIST><NAME>Widget A</NAME></NAME.LIST>
 </LANGUAGENAME.LIST>
 <PARENT>Hardware</PARENT>
 <BASEUNITS>PCS</BASEUNITS>
 <ADDITIONALUNITS>CASE</ADDITIONALUNITS>
 <DENOMINATOR>12</DENOMINATOR>   <!-- "1 CASE = 12 PCS" — see note below -->
 <CONVERSION>1</CONVERSION>      <!-- always 1 on the stock item side -->
 <GSTTYPEOFSUPPLY>Goods</GSTTYPEOFSUPPLY>

 <OPENINGBALANCE>100 PCS</OPENINGBALANCE>
 <OPENINGRATE>50/PCS</OPENINGRATE>
 <OPENINGVALUE>-5000</OPENINGVALUE>  <!-- negative for normal owned stock! see Sign Conventions -->

 <HSNDETAILS.LIST>
  <APPLICABLEFROM>20250401</APPLICABLEFROM>
  <HSNCODE>39061000</HSNCODE>
  <SRCOFHSNDETAILS>Specify Details Here</SRCOFHSNDETAILS>  <!-- REQUIRED, see below -->
 </HSNDETAILS.LIST>

 <GSTDETAILS.LIST>
  <APPLICABLEFROM>20250401</APPLICABLEFROM>
  <TAXABILITY>Taxable</TAXABILITY>
  <SRCOFGSTDETAILS>Specify Details Here</SRCOFGSTDETAILS>   <!-- REQUIRED, see below -->
  <STATEWISEDETAILS.LIST>
   <STATENAME>&#4; Any</STATENAME>   <!-- literal control-char prefix, see Gotchas -->
   <RATEDETAILS.LIST>
    <GSTRATEDUTYHEAD>CGST</GSTRATEDUTYHEAD>
    <GSTRATEVALUATIONTYPE>Based on Value</GSTRATEVALUATIONTYPE>
    <GSTRATE>9</GSTRATE>
   </RATEDETAILS.LIST>
   <RATEDETAILS.LIST>
    <GSTRATEDUTYHEAD>SGST/UTGST</GSTRATEDUTYHEAD>
    <GSTRATEVALUATIONTYPE>Based on Value</GSTRATEVALUATIONTYPE>
    <GSTRATE>9</GSTRATE>
   </RATEDETAILS.LIST>
   <RATEDETAILS.LIST>
    <GSTRATEDUTYHEAD>IGST</GSTRATEDUTYHEAD>
    <GSTRATEVALUATIONTYPE>Based on Value</GSTRATEVALUATIONTYPE>
    <GSTRATE>18</GSTRATE>
   </RATEDETAILS.LIST>
  </STATEWISEDETAILS.LIST>
 </GSTDETAILS.LIST>
</STOCKITEM>
SRCOFGSTDETAILS (and SRCOFHSNDETAILS) are undocumented but required. Omit SRCOFGSTDETAILS and the entire STATEWISEDETAILS.LIST — including every RATEDETAILS.LIST entry — is silently dropped, even though TAXABILITY saves fine on its own. The value Tally's own UI uses is the literal string "Specify Details Here".
DENOMINATOR / CONVERSION are easy to get backwards. For "1 CASE = 12 PCS": DENOMINATOR = 12 (the base-unit count), CONVERSION = 1. Swapping them (DENOMINATOR=1, CONVERSION=12) silently produces the inverse ratio — 100 PCS became "1200 CASE" instead of "8 CASE" in testing.

Create a Group / Stock Group / Stock Category

All three share the same minimal shape — just swap the tag name (GROUP, STOCKGROUP, STOCKCATEGORY):

<STOCKGROUP NAME="Hardware" ACTION="Create">
 <LANGUAGENAME.LIST>
  <NAME.LIST><NAME>Hardware</NAME></NAME.LIST>
 </LANGUAGENAME.LIST>
 <PARENT>&#4; Primary</PARENT>   <!-- top-level: literal control-char prefix -->
</STOCKGROUP>
Plain "Primary" as the parent is rejected. <PARENT>Primary</PARENT> fails with LINEERROR: Stock Group 'Primary' does not exist! — Tally requires the literal string "\x04 Primary" (control character 0x04, a space, then "Primary"), the same reserved-value convention as the GST "Any" state above. For a real (non-top-level) parent, just use its plain name.

Create a Unit

<UNIT NAME="SET" ACTION="Create">
 <NAME>SET</NAME>                <!-- flat <NAME>, NOT LANGUAGENAME.LIST — see below -->
 <ISSIMPLEUNIT>Yes</ISSIMPLEUNIT>
 <DECIMALPLACES>0</DECIMALPLACES>
 <REPORTINGUQCDETAILS.LIST>
  <APPLICABLEFROM>20250401</APPLICABLEFROM>
  <REPORTINGUQCNAME>SET-SETS</REPORTINGUQCNAME>
 </REPORTINGUQCDETAILS.LIST>
</UNIT>
Units are the one master type that rejects the LANGUAGENAME.LIST pattern. Wrapping the name in LANGUAGENAME.LIST/NAME.LIST (which works for every other type) fails with LINEERROR: BAD UNIT NAME — use a flat <NAME> instead. As a consequence, Units also have no working alias mechanism: neither the flat <ALIAS> tag nor NAME.LIST persists one.
Unit symbols can't contain spaces. <UNIT NAME="MY UNIT"> fails with LINEERROR: BAD UNIT NAME even with a flat <NAME>. Real Tally units are always short codes (PCS, KGS, BOX…).

Renaming a Record

The tag's NAME attribute identifies which existing record to alter — it is not "the new name". To rename, keep the attribute pointing at the old name and put the new name in the body:

<LEDGER NAME="ZZ Old Name" ACTION="Alter">
 <NAME>ZZ New Name</NAME>
 <PARENT>Sundry Debtors</PARENT>
 <!-- ...every other field you want to keep, same as Create... -->
</LEDGER>
Confirmed live on Ledger, Stock Item, and Unit. The result is a single renamed record with its GUID unchanged and all nested data (GST details, HSN, opening balances) intact — no orphaned duplicate left behind under the old name.

Deleting a Record

<LEDGER NAME="ZZ Test" ACTION="Delete">
 <NAME>ZZ Test</NAME>
</LEDGER>

Works the same way for every master type. Deletion fails (with a LINEERROR) if the record is referenced elsewhere — e.g. a ledger with posted vouchers, or a group with ledgers still under it.

Create a Voucher — simple types Payment / Receipt / Contra / Journal

Vouchers use the same IMPORTDATA envelope as masters, but the REPORTNAME must be Vouchers — "All Masters" (which works fine for every master type above) does not. For accounting-only voucher types with no items involved, a hand-built minimal body works reliably:

<VOUCHER VCHTYPE="Journal" ACTION="Create">
 <DATE>20260401</DATE>                        <!-- YYYYMMDD, same as every master date -->
 <VOUCHERTYPENAME>Journal</VOUCHERTYPENAME>
 <PERSISTEDVIEW>Accounting Voucher View</PERSISTEDVIEW>  <!-- required -->
 <NARRATION>Being expense accrual</NARRATION>
 <ALLLEDGERENTRIES.LIST>
  <LEDGERNAME>Rent Expense</LEDGERNAME>
  <ISDEEMEDPOSITIVE>Yes</ISDEEMEDPOSITIVE>   <!-- Yes = Debit -->
  <AMOUNT>-5000</AMOUNT>                     <!-- negative on the Debit side -->
 </ALLLEDGERENTRIES.LIST>
 <ALLLEDGERENTRIES.LIST>
  <LEDGERNAME>Outstanding Liabilities</LEDGERNAME>
  <ISDEEMEDPOSITIVE>No</ISDEEMEDPOSITIVE>    <!-- No = Credit -->
  <AMOUNT>5000</AMOUNT>                      <!-- positive on the Credit side -->
 </ALLLEDGERENTRIES.LIST>
</VOUCHER>

Works exactly the same for VCHTYPE="Payment", "Receipt", "Contra" — just add a <PARTYLEDGERNAME> tag if there's a natural party. No GST/status scaffolding is needed for these — unlike Sales/Purchase (next section), the request above is genuinely sufficient by itself.

The misleading LINEERROR: Voucher date is missing ... retry Split error is not about a missing date field. Two completely unrelated causes produce this exact same message:
  1. A license/edition date cutoff — a TallyPrime EDU (free/educational) installation only accepts voucher dates up to a fixed point tied to the license; every date after that fails with this error, for every voucher type, including the plain Journal example above. Bisect a working date (e.g. today minus 30/60/90 days) before assuming your XML shape is wrong.
  2. For Sales/Purchase/Credit Note/Debit Note specifically: missing GST context fields — see the next section. Here the date itself is fine; Tally's GST "Split" computation is failing for an unrelated reason and surfaces the same generic text.

Create a Voucher — item-invoice types Sales / Purchase

A hand-built minimal XML body does NOT work for Sales/Purchase, no matter how many fields you add. This is the single most time-consuming finding on this page. Item-invoice vouchers (PERSISTEDVIEW=Invoice Voucher View) run through Tally's GST "Split" computation, which needs a large web of company/party GST context fields (party GSTIN/state/address, the company's own GST registration, VCHENTRYMODE, several tax-adjustment status fields...). Adding every field visible in a real export — all of them, individually confirmed relevant — still wasn't enough; the request kept getting silently rejected (EXCEPTIONS>1, usually with no error text at all).

The only approach confirmed to work reliably: clone a real existing voucher of that type and substitute values into it, keeping its ~150 other fields byte-for-byte as Tally itself wrote them.

  1. Export one real voucher of the target type (REPORTNAME=Voucher Register, VOUCHERTYPENAME static variable, a single-day date range — see the performance warning below) and grab its full <VOUCHER>...</VOUCHER> block as raw text.
  2. Strip the REMOTEID="..." and VCHKEY="..." attributes from the opening tag (leaving them in causes Tally to silently Create a duplicate instead of matching the intended record — relevant for editing too, see below).
  3. String-replace (not an XML-tree re-serialize — see gotcha below) the specific tags that need to change: DATE, EFFECTIVEDATE, VCHSTATUSDATE, NARRATION, the party's name/GSTIN/state/pincode/address fields, and remove VOUCHERNUMBER entirely so Tally auto-assigns the next one (keeping the cloned number verbatim creates a duplicate voucher number).
  4. Strip every original <ALLINVENTORYENTRIES.LIST> and <LEDGERENTRIES.LIST> block and rebuild your own for the new items/party (shape below) — everything else in the template stays untouched.
<!-- rebuilt item block, inserted where the template's originals were -->
<ALLINVENTORYENTRIES.LIST>
 <STOCKITEMNAME>Widget A</STOCKITEMNAME>
 <ISDEEMEDPOSITIVE>No</ISDEEMEDPOSITIVE>   <!-- Sales: No (Credit). Purchase: Yes (Debit). -->
 <RATE>100/PCS</RATE>
 <AMOUNT>200</AMOUNT>                      <!-- Sales: positive. Purchase: negative. See Sign Conventions. -->
 <ACTUALQTY>2 PCS</ACTUALQTY>               <!-- qty stays POSITIVE regardless of direction -->
 <BILLEDQTY>2 PCS</BILLEDQTY>
 <ACCOUNTINGALLOCATIONS.LIST>               <!-- REQUIRED nested block, not a flat top-level entry -->
  <LEDGERNAME>Sales Account</LEDGERNAME>
  <ISDEEMEDPOSITIVE>No</ISDEEMEDPOSITIVE>
  <AMOUNT>200</AMOUNT>
 </ACCOUNTINGALLOCATIONS.LIST>
</ALLINVENTORYENTRIES.LIST>

<!-- party entry - note the tag name Tally's own export uses here is
     LEDGERENTRIES.LIST, not ALLLEDGERENTRIES.LIST (which is what the
     simple voucher types above use) -->
<LEDGERENTRIES.LIST>
 <LEDGERNAME>Some Customer</LEDGERNAME>
 <ISDEEMEDPOSITIVE>Yes</ISDEEMEDPOSITIVE>   <!-- Sales: Yes (party Dr). Purchase: No (party Cr). -->
 <AMOUNT>-200</AMOUNT>
</LEDGERENTRIES.LIST>
Never fetch the template with a wide date range on a high-volume voucher type. Voucher Register dumps every field for every match — the same wildcard-fetch trap as Stock Items (see Gotchas). Querying a full financial year of Sales (1000+ vouchers) hung the XML server for several minutes and needed a Tally restart to recover. Always scope this export to a single day: find one voucher's date cheaply first (a lean Collection query), then re-fetch just that day in full detail.
This only works for a voucher type the company already has at least one real example of. There's no way to clone-and-substitute for a type with zero existing vouchers (e.g. Credit Note/Debit Note in a company that's never used them) — you'd need to manually enumerate the full GST scaffolding from Tally's own documentation or a different reference company, neither of which was attempted here.

Editing a Voucher ACTION=Alter

Vouchers have no NAME attribute to key off — Tally itself calls them "unnamed" objects. Identification for Alter/Delete is a completely different mechanism from every master type above: attributes on the <VOUCHER> tag itself, not a body field.

<VOUCHER DATE="02-Apr-2026" TAGNAME="Master Id" TAGVALUE="6491"
         VCHTYPE="Sales" ACTION="Alter">
 <!-- full body, same shape as Create -->
</VOUCHER>
AttributeNotes
DATEthe voucher's current date, format dd-MMM-yyyy (e.g. "02-Apr-2026") — different from the nested <DATE> field's YYYYMMDD format used everywhere else.
TAGNAMEwhich identifier TAGVALUE is. Tally's docs list "Master Id", "Voucher Number", "Reference", "Narration" as valid options.
TAGVALUEthe identifier's value.
Use TAGNAME="Master Id", not "Voucher Number". "Voucher Number" works fine for simple sequentially-numbered types (Journal, Contra) but silently no-ops for a voucher under "Automatic (Manual Override)" numbering (Sales/Purchase) — the response reports ALTERED>1/DELETED>1 with no error, but nothing actually changes. MASTERID (Tally's own true internal id — fetch it via a MASTERID <FETCH> on the read side) worked reliably across every voucher type tried.
REMOTEID/VCHKEY do NOT work for identification at all — every attempt against them fails with LINEERROR: Voucher does not exist!, even quoting them back exactly as Tally's own export showed, including after a full Tally restart. They're export-only fields, not a valid lookup key for Import.
If cloning the voucher's own XML to edit it (Sales/Purchase — same technique as Create above), you MUST strip REMOTEID/VCHKEY from the clone before submitting. Leaving them in makes Tally silently Create a duplicate voucher instead of matching-and-altering the original — TAGNAME/TAGVALUE gets ignored in favor of (broken) REMOTEID matching. Confirmed live: same symptom either way (a new voucher with the original's data, response says CREATED>1 not ALTERED>1) whether editing a simple or item-invoice type.

Deleting a Voucher ACTION=Delete

<VOUCHER DATE="02-Apr-2026" TAGNAME="Master Id" TAGVALUE="6491"
         VCHTYPE="Contra" ACTION="Delete">
</VOUCHER>

Same identification rules as Alter above (use Master Id, include the empty body). Response on success: <DELETED>1</DELETED>. Confirmed to actually remove the record — verified via re-read through both the fast Collection query and the Voucher Register report, and visually in Tally's own Day Book.

Gotchas & Quirks — Quick Index

  1. Silent failures on write. A "successful" CREATED>1 response can still have silently dropped fields. Always read back what you wrote.
  2. History-tracked nested lists need APPLICABLEFROM. LEDMAILINGDETAILS.LIST, LEDGSTREGDETAILS.LIST, HSNDETAILS.LIST, GSTDETAILS.LIST, REPORTINGUQCDETAILS.LIST all need this date, and it must equal the company's actual books-from date — not "today".
  3. Alias = 2nd <NAME> in NAME.LIST, not a flat <ALIAS> tag — except Units, which support no alias mechanism at all.
  4. Reserved values need a literal control character. "Applies to all states" is the literal string "\x04 Any" (0x04 + space + "Any"); a top-level group's parent is "\x04 Primary". Plain text without the control character is rejected outright (not silently dropped — you get a LINEERROR).
  5. SRCOFGSTDETAILS / SRCOFHSNDETAILS are undocumented-but-required fields inside GSTDETAILS.LIST / HSNDETAILS.LIST — omit them and the whole rate/HSN block is dropped.
  6. Company's own GSTIN lives on a separate TAXUNIT object, not on Company itself (Company/GSTREGISTRATIONNUMBER is reliably empty in TallyPrime 5+).
  7. Company's address is REMOTEFULLLISTNAME (one flattened comma-joined string) — ADDRESS.LIST only works for Ledgers.
  8. Party GSTIN is under LEDGSTREGDETAILS.LIST/GSTIN, not the flat (legacy, always-empty) PARTYGSTIN field.
  9. Stock item alt-unit ratio is DENOMINATOR/CONVERSION on the item itself — the Unit master's own same-named fields are for genuine compound units and are unrelated.
  10. Unit names can't contain spaces and reject the NAME.LIST alias pattern that every other master accepts.
  11. Rename ≠ edit-then-save. The tag's NAME attribute must stay the old name to identify the record; the new name goes in the body.
  12. Ledger's live state is often on PRIORSTATENAME, not STATENAME. Fetch both and fall back.
  13. Wildcard FETCH * + date range on StockItem can hang the XML server for a minute or more across a large item catalog. Never combine them.
  14. Vouchers need REPORTNAME=Vouchers for Import, not "All Masters".
  15. LINEERROR: Voucher date is missing ... retry Split is almost never about a missing date. It's the generic error for two unrelated causes: a TallyPrime EDU license's date cutoff (affects every voucher type identically), or missing GST context on a Sales/Purchase voucher. See Create a Voucher.
  16. Sales/Purchase can't be hand-built from a minimal field set, ever. Clone a real voucher of that type and substitute values in — see Create a Voucher (Sales/Purchase).
  17. Voucher Alter/Delete identification is TAGNAME/TAGVALUE attributes on the tag, not the NAME attribute masters use, and not REMOTEID/VCHKEY (which reliably fail with "Voucher does not exist!"). Use TAGNAME="Master Id" — "Voucher Number" silently no-ops for Sales/Purchase's numbering style.
  18. A string-substitution regex like <TAG>.*?</TAG> won't match Tally's self-closing empty tags (<NARRATION/>) — if you're cloning-and-substituting XML text rather than using a proper XML parser, match <TAG>.*?</TAG>|<TAG/> or the substitution silently no-ops whenever the template's original value was empty.
  19. Leaving a cloned voucher's REMOTEID/VCHKEY in place for an Alter makes Tally silently Create a duplicate instead — strip both before submitting, for Create and Alter.

Date formats — there are two, not one

Almost every Tally date in XML is YYYYMMDD with no separators, e.g. 20250401 for 1 April 2025 — this covers every master field and a voucher's own nested <DATE> field. The one exception: the DATE attribute used to identify an existing voucher for Alter/Delete (alongside TAGNAME/TAGVALUE) is dd-MMM-yyyy, e.g. "02-Apr-2026" — see Editing a Voucher.
